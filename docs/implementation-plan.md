# План разработки Wordle в HTML-виджете Telegram

Дата: 9 ноября 2026 года. Статус: план подготовлен; реализация не начата.

Уточнение пользователя: библиотека Python-бота — **aiogram 3.x**. Это решение заменяет первоначальный вариант самостоятельных HTTP-запросов.

Документ предназначен для последовательной разработки первой рабочей версии. Он опирается на [согласованное описание игры](design.md) и [словарь терминов](../GLOSSARY.md). Правила из интервью считаются установленными; технические детали ниже задают способ их реализации.

Целевые клиенты: **Telegram Desktop на Windows и Telegram на Android**. Это уточнено пользователем при подготовке плана.

## 1. Результат первой версии

Пользователь запускает бота на своём компьютере, отправляет `/start` в личном чате и получает сообщение с Wordle. Внутри сообщения находятся поле, русская клавиатура и кнопка «Новая игра». После доставки виджета партия обрабатывается на устройстве пользователя.

| Требование | Поведение |
| --- | --- |
| R1. Формат | HTML-виджет непосредственно в сообщении бота |
| R2. Ответы | Небольшой список простых русских существительных: пять букв, единственное число, именительный падеж |
| R3. Алфавит | Русские буквы; Ё нормализуется в Е; отображение в верхнем регистре |
| R4. Попытки | Шесть принятых попыток на партию |
| R5. Проверка ввода | Любые пять русских букв принимаются и расходуют попытку; наличие слова в словаре не проверяется |
| R6. Подсказки | Классические зелёный, жёлтый и серый цвета с правильным учётом повторяющихся букв |
| R7. Новая игра | Доступна в любой момент и начинает новую партию в том же виджете |
| R8. Завершение | При победе или исчерпании попыток показывается ответ, дальнейшие попытки блокируются |
| R9. Жизненный цикл | При временном сворачивании партия остаётся; после перезапуска приложения начинается заново |
| R10. Локальность | Партия не переносится между устройствами и не хранится у бота |
| R11. Запуск | Python-бот работает локально, пока запущена программа |
| R12. Интерфейс | Поле 6 × 5, кнопочная клавиатура, светлая и тёмная темы; проверка на Windows и Android |

В первую версию не входят ежедневное слово, статистика за несколько дней, таблица лидеров, мультиплеер, платежи и постоянный хостинг. В интервью эти возможности не запрашивались.

## 2. Технические ограничения и ранняя проверка

Ограничения проверены по официальной документации на дату плана. Перед первой интеграцией сверить их повторно: возможность новая.

| Ограничение | Решение для проекта |
| --- | --- |
| Виджет автономен, без сетевого доступа | Список ответов, стили и игровая логика включаются в HTML |
| Текстового ввода с клавиатуры нет | Использовать кнопки; не использовать `input`, `textarea` и обработчики клавиатуры |
| HTML ≤ 32 768 байт UTF-8; zlib уровня 9 ≤ 4096 байт | Проверять оба размера при сборке; целевой сжатый размер — до 3800 байт |
| Высота до 600 px | Целиться в высоту до 560 px при ширине 320 px; проверить узкое сообщение |
| Код отправленного сообщения неизменяем | После обновления кода отправлять новый виджет командой `/start` |
| `sessionStorage` относится к сообщению на устройстве и живёт до перезапуска приложения | В нём держать текущую партию и восстанавливать её при создании виджета |

Источник: [Telegram Widgets](https://core.telegram.org/bots/widgets), разделы Sizes, Storage, Lifecycle и Counting the size.

Для отправки используется `sendWidget`: обязательные параметры — `chat_id` и `html`. Передавать короткую подпись с правилами; ширину и высоту сначала оставить автоматическими. `allow_queries` и `is_shared` не включать; игровые данные не отправлять в `chat_data` и `public_data`. Production сейчас поддерживает личные чаты. Источник: [Bot API — sendWidget](https://core.telegram.org/bots/api#sendwidget).

**Первый технический рубеж:** минимальный интерактивный виджет успешно доставлен и работает на обоих целевых клиентах. До этого не тратить время на полировку игры. Если API или клиент не поддерживает виджет, записать точную ошибку и версии клиентов; замену формата на Mini App согласовать отдельно.

## 3. Архитектура и границы ответственности

| Часть | Ответственность | Данные |
| --- | --- | --- |
| Python-бот на aiogram | Получить `/start`, собрать HTML, отправить сообщение | Токен, конфигурация; получение обновлений управляется aiogram |
| Сборщик виджета | Объединить шаблон, CSS, JavaScript и ответы; проверить ограничения | Исходные файлы, итоговый HTML, отчёт размеров |
| Игровая модель JavaScript | Принять попытку, посчитать подсказки, определить исход, начать новую партию | Ответ, попытки, текущий ввод |
| Работа с временным хранилищем | Записать и восстановить партию | Один версионированный JSON-объект в `sessionStorage` |
| Интерфейс JavaScript/CSS | Нарисовать поле и клавиатуру; обработать нажатия и результат | Производное представление игровой модели |

Бот не выбирает ответы для отдельных партий и не получает нажатия букв. После доставки виджета новые партии не требуют работающего процесса бота. Для получения нового сообщения через `/start` процесс нужен.

Технологии для реализации:

- Python 3.13 и aiogram 3.x: `Bot` для Bot API, `Dispatcher` и `Router` для команд, `CommandStart` для `/start`. JSON и проверка размеров — стандартные `json` и `zlib`.
- Получение команд через `Dispatcher.start_polling`; HTTP-сессией управляет aiogram. Самостоятельный цикл `getUpdates` и отдельный HTTP-клиент не писать.
- Обычный JavaScript, CSS и HTML без внешних библиотек, шрифтов и ресурсов.
- Python-проверки через `unittest`, асинхронные сценарии через `IsolatedAsyncioTestCase`; JavaScript-проверки через встроенный `node:test`. Node нужен для разработки и проверок; для запуска бота нужны Python и установленные зависимости aiogram.
- Проверенное локальное окружение: Python 3.13.7 в `.venv`, Node.js v24.22.1. Наличие окружения не означает, что код или проверки уже созданы.

### Совместимость aiogram с новым методом

На дату проверки официальная документация aiogram 3.31.0 заявляет Bot API 10.3; в проверенном списке методов `sendWidget` отсутствует. Это состояние документации на дату плана, а не запрет на использование библиотеки. Источники: [aiogram](https://docs.aiogram.dev/en/latest/) и [список методов](https://docs.aiogram.dev/en/latest/api/methods/index.html).

На этапе 0 проверить актуальный стабильный выпуск 3.x и закрепить точные версии зависимостей в `requirements.txt`. Если готовый `SendWidget` уже появился, использовать его. В противном случае определить небольшой метод на основе `TelegramMethod[Message]` с именем API `sendWidget`, нужными полями и выполнением через `Bot` и его штатную сессию. Проверить сериализацию запроса и разбор ответа, содержащего поле `widget`. Основание для расширения — [исходник TelegramMethod](https://github.com/aiogram/aiogram/blob/v3.31.0/aiogram/methods/base.py). Общий транспорт и обработку ошибок библиотеки не копировать.

Команды и отправка виджета должны работать через aiogram при обоих вариантах. FSM, Redis и серверное хранение партий для согласованной игры не нужны.

## 5. Контракт игровой модели

### Ввод и попытка

- Нормализация: верхний регистр, замена Ё на Е.
- Кнопки букв добавляют символы до длины пять; удаление убирает последний символ.
- «Ввод» принимает ровно пять русских букв, включая Ъ, Ы и Ь. Ввод другой длины или с другими символами не расходует попытку.
- Принятая последовательность попадает в следующую строку; ввод очищается.
- Повтор той же последовательности разрешён и снова расходует попытку.
- Сначала проверяется победа; только затем — исчерпание попыток. Успех на шестой попытке считается победой.
- В завершённой партии кнопки ввода и удаления не изменяют состояние; «Новая игра» остаётся доступной.

### Подсказки и клавиатура

Расчёт состоит из двух проходов: сначала отметить точные совпадения и вычесть их из количества букв ответа; затем слева направо раздать жёлтые подсказки по оставшимся количествам. Остальные буквы серые.

Подсветка клавиши объединяет все принятые попытки: зелёный имеет приоритет над жёлтым, жёлтый — над серым. Уже известная зелёная клавиша не становится серой после другой попытки.

Контрольные примеры для ответа **ЛАМПА**:

| Попытка | Ожидаемые подсказки слева направо |
| --- | --- |
| ЛАМПА | зелёный, зелёный, зелёный, зелёный, зелёный |
| ПАЛКА | жёлтый, зелёный, жёлтый, серый, зелёный |
| ААААА | серый, зелёный, серый, серый, зелёный |
| БББББ | серый, серый, серый, серый, серый; попытка расходуется |

### Выбор ответа

Начальный ориентир — 100 вручную проверенных простых слов. Это размер списка для первой сборки, а не новое правило игры. Сборщик нормализует ответы и отклоняет дубликаты, пустой список, неверную длину и посторонние символы. Редкость слова и правильность грамматической формы проверяются вручную.

Ответ выбирается случайно из встроенного списка. При «Новой игре» исключить текущий ответ, если в списке больше одного слова. Более ранние ответы могут повторяться. После перезапуска история выбора отсутствует.

## 6. Контракт временного состояния

Хранить один объект с полями `version`, `answer`, `guesses` и `input`. Статус партии и цвета вычислять по ответу и принятым попыткам; не хранить их второй независимой копией.

- Записывать изменения после каждой буквы, удаления, принятой попытки и новой игры.
- При создании виджета сначала читать состояние, затем рисовать поле.
- Проверять версию, принадлежность ответа встроенному списку, допустимость ввода и попыток, отсутствие ходов после победы и превышения лимита.
- При отсутствии или повреждении данных начинать новую партию. Не использовать `localStorage`, сервер или файл бота для обходного сохранения.
- События скрытия и возврата не сбрасывают партию. Отдельный обработчик «закрытия приложения» не нужен.
- Если временное хранилище недоступно или запись не удалась, игра продолжает работать в памяти и показывает короткое сообщение о невозможности удержать прогресс при выгрузке. Ошибка не должна останавливать виджет.
- Два сообщения с игрой имеют независимые партии. Повторный `/start` создаёт новое сообщение; существующее не заменяется.

Полный перезапуск означает завершение и новый запуск приложения. Закрытие окна в трей на Windows не является завершением. Если Android фактически завершил Telegram в фоне, следующее открытие тоже считается перезапуском. Удаление сообщения или данных приложения не входит в гарантию удержания партии.

## 7. Контракт бота и сборки

### Конфигурация и команды

- Единственная обязательная настройка — переменная окружения `BOT_TOKEN`. Значение пользователь задаёт локально; токен не включать в документы, код, тестовые данные и журнал.
- На старте проверить конфигурацию, создать `Bot`, выполнить его `get_me()` и `get_webhook_info()`. Существующий webhook автоматически не удалять; показать причину остановки и инструкцию в README.
- Запустить `Dispatcher.start_polling` с `allowed_updates=["message"]`, согласованными таймаутами polling и сессии. Получение обновлений, курсор и повторные попытки polling поручить aiogram. Источник: [aiogram — Long-polling](https://docs.aiogram.dev/en/latest/dispatcher/long_polling.html).
- Зарегистрировать `/start` через `CommandStart` и фильтр личного чата. Команда, включая аргумент после неё, отправляет новый игровой виджет. Для другого текста в личном чате дать короткую подсказку использовать `/start`; неподдерживаемые типы сообщений пропускать. В группах игру не отправлять.
- Обрабатывать сетевые ошибки и ошибки Bot API средствами aiogram; для 429 при отправке учитывать `TelegramRetryAfter.retry_after`. Неверный токен останавливает запуск; конфликт второго процесса polling должен иметь понятную диагностику. Не добавлять второй цикл повторов поверх штатного механизма polling.
- Не повторять `sendWidget` вслепую после неоднозначного сетевого таймаута: сообщение могло уже уйти. Записать понятную ошибку и предложить повторить `/start`. Не обещать строго однократную доставку после аварийного перезапуска процесса.
- Остановка через Ctrl+C завершается без длинного traceback; сессия `Bot` закрывается штатными средствами aiogram. Не выводить полный URL запроса с токеном.

### Сборка

- Встроить CSS, игровые модули и список ответов в шаблон; в отправляемом HTML не оставлять внешних ссылок на ресурсы и незаменённых маркеров.
- Сначала проверять словарь и валидность UTF-8, затем оба размера из раздела 2. Считать именно байты готового HTML, а не количество символов или размер исходных файлов.
- Один и тот же путь сборки использовать в проверке, при записи `build/widget.html` и при отправке ботом. Не поддерживать отдельно «тестовый» и «настоящий» HTML.
- При выходе за лимит остановить сборку с обоими измерениями. Сначала упрощать оформление и вспомогательные тексты; сокращение списка ответов явно отражать в отчёте. Не менять правила и не переходить к серверным партиям автоматически.
- Не применять самодельное удаление пробелов регулярными выражениями к JavaScript. Для первой версии достаточно шаблона без лишнего содержимого и штатного сжатия для измерения.

## 9. Проверки и критерии приёмки

### Автоматические команды после реализации

После создания `requirements.txt` один раз установить закреплённые зависимости:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Проверки из корня проекта на Windows:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests/python -v
node --test
.\.venv\Scripts\python.exe -m wordle_bot.widget --check
```

Будущие команды сборки и запуска:

```powershell
.\.venv\Scripts\python.exe -m wordle_bot.widget --output build/widget.html
.\.venv\Scripts\python.exe -m wordle_bot
```

Эти команды задают интерфейс будущих модулей. На момент составления плана модулей ещё нет; успешное выполнение не заявляется.

В автоматическом наборе обязательны: приём бессмысленных последовательностей, неверная длина и алфавит, Ё/Е и регистр, повторяющиеся буквы, победа на шестой попытке, проигрыш, запрет ходов после исхода, новая игра, приоритет цветов клавиш, восстановление временного состояния и сбои хранилища. Для бота проверять фактические запросы штатной сессии aiogram и разбор ответов на локальном сервере, маршрутизацию через `Dispatcher.feed_update`; для сборки — готовый HTML и выход за лимиты. Внешний Telegram в модульные тесты не включать. Не тестировать внутренний алгоритм polling библиотеки как собственную реализацию.

### Ручная матрица

В `docs/validation.md` создать колонки: сценарий, Windows, Android, замечание. Каждый результат содержит дату и фактический итог.

| Сценарий | Ожидаемый результат |
| --- | --- |
| Отправить `/start` | Виджет внутри сообщения, все элементы доступны |
| Ввести пять любых букв, включая бессмыслицу | Строка принята, одна попытка потрачена |
| Ввести меньше пяти букв и нажать ввод | Попытка не расходуется, понятна причина |
| Выиграть, в том числе на шестой попытке | Показаны победа и ответ; дополнительные ходы запрещены |
| Сделать шесть неверных попыток | Показаны проигрыш и ответ; дополнительные ходы запрещены |
| Проверить слово с повторяющимися буквами | Число жёлтых и зелёных отметок соответствует числу букв в ответе |
| Начать новую игру в процессе и после исхода | Поле, ввод и подсветка очищены; новая партия доступна |
| Свернуть и вернуть приложение | Ответ, попытки и незавершённый ввод остались |
| Уйти в другой чат, прокрутить далеко и вернуться | Партия восстановилась при живом сеансе приложения |
| Полностью завершить Telegram и открыть заново | У того же сообщения началась пустая партия; новое случайное слово может совпасть со старым |
| Открыть игру на другом устройстве | Независимая партия, без переноса прогресса |
| Отправить `/start` повторно | Отдельное сообщение; старая партия не меняется |
| Переключить светлую и тёмную темы | Поле, буквы, клавиши и исход читаемы |
| Узкое окно Windows, обычный экран Android, крупный текст | Нет обрезанных строк и недоступных кнопок |
| Остановить Python-бота после доставки | Полученный виджет продолжает принимать попытки и начинать новые партии |
| Изменить сборку и снова отправить `/start` | Новое сообщение содержит новую версию; старое сохраняет прежний код |

Для сценариев с известным ответом использовать тестовую сборку с одним ответом. После них повторить обычную случайную игру на финальной сборке; тестовый ответ и вспомогательные элементы не должны попасть в неё.

## 10. Как пользоваться планом

1. Выполнять этапы по зависимостям. Сначала фиксировать проверяемое поведение, затем реализовывать его и получать результат проверки.
2. Закрывать пункт по наблюдаемому результату, а этап — по его критерию готовности. Команда запуска без подтверждённого результата не считается проверкой.
3. В `docs/validation.md` вести фактические результаты; этот документ сохранять как план работ.
4. Если меняется правило игры, сначала обновить `design.md`, затем соответствующие пункты плана. Техническую корректировку файлов можно внести прямо здесь с кратким объяснением.
5. Реализация считается завершённой после этапа 7. Написанный код без проверки в целевых клиентах считать промежуточным результатом.
